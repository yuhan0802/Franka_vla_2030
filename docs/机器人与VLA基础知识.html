机器人与 VLA 部署基础知识

面向第一次接触机器人控制的同学，解释本项目（Franka FR3 + 试管抓取 VLA）里反复出现的概念。每个概念都配本项目的实例：日志字段、遇到过的问题和对应文件。建议顺序：先看第 1 章全貌，再看第 2～4 章坐标系与旋转（最容易出错），然后第 5～7 章机器人怎么动、第 8～10 章模型怎么出动作，最后第 12 章怎么排查。

1. 整条链路长什么样

一次推理到机械臂动起来，经过下面这些环节：

  • 观测（observation）：模型看到的东西——两张图 + 机器人当前状态 + 任务指令文字。
  • 动作（action）：模型输出的东西——接下来 1 秒内每一小步该怎么动。
  • adapter：本项目是 eef_pose_policy_adapter.py / eef_pose_direct_adapter.py。
  • 模型服务：本项目是 deploy_franka_task0_qwen_actioncodec_eef.py、deploy_droid_qwen_actioncodec_eef.py，通过 WebSocket 收观测、回动作。
最重要的原则：训练和部署必须对齐。模型只认识训练时见过的输入格式。图像尺寸、指令文字、坐标系、单位、频率、夹爪编码只要有一处不同，模型就会"看错"或"做错"，而且通常不报错。本项目前后修的问题，大部分都属于这一类。

2. 坐标系（frame）

"往前 3 cm" 必须说清楚是谁的前。机器人里每个关键部件都有自己的坐标系：三根互相垂直的轴 x / y / z 加一个原点。一个位置或方向只有指定了坐标系才有意义。

名称在哪说明
world / base机械臂底座固定不动，本项目两者重合。x 朝前、y 朝左、z 朝上
fr3_link0～fr3_link7每节臂随关节转动
fr3_link8（法兰）末端安装面本项目的"末端"，状态和目标位姿都用它
fr3_hand_tcp（TCP）夹爪两指中心Tool Center Point，工具中心点
相机坐标系各相机相机自己的坐标系

位姿（pose） = 位置 (x, y, z) + 姿态（朝向）。日志里的 armed at [0.5581, -0.0017, 0.3225] 就是 fr3_link8 在 world 里的位置，单位米。

TF 树

ROS 用 TF 记录所有坐标系之间的关系，组成一棵树：world → base → fr3_link0 → … → fr3_link8 → fr3_hand → fr3_hand_tcp。关节一动，robot_state_publisher 就根据关节角实时更新这棵树。日志里的 waiting for world -> fr3_link8 表示树还没建好；… is 1.033s old 表示数据太旧。

为什么要分清法兰和 TCP

同样转 0.1 rad，绕法兰转和绕夹爪中心转，指尖位置会差 0.1 × 10 cm ≈ 1 cm。所以训练数据用哪个点当末端，部署就必须用哪个点。本项目核实过：Task0 数据和 DROID 数据都用法兰 link8，所以不需要 TCP 外参。

3. 姿态的几种表示方法

同一个朝向可以写成好几种不同的数字。混用表示方法，是最常见的 bug 来源之一。

表示几个数特点本项目里
欧拉角 / RPY3直观；但转动顺序和"绕固定轴还是绕自身轴"有多种约定，约定不同结果完全不同DROID 数据，用 from_euler("xyz") 读，小写表示绕固定轴

4. 旋转的合成：左乘与右乘

这是本项目花时间最多的问题。已知当前姿态 R，要再转一个小增量 Δ，有两种做法：

增量怎么算出来的，就要怎么用回去

录制时怎么算增量属于部署时
Δ = R_cur × R_prev⁻¹世界系增量左乘 R_new = Δ × R
Δ = R_prev⁻¹ × R_cur工具系增量右乘 R_new = R × Δ
本项目录制器的注释写的是第一种，代码实际算的是第二种。用录制数据逐帧验证：按右乘复现，误差 ≤3e-7 rad；按左乘，误差 0.02～0.04 rad。所以 Task0 权重部署时用右乘（日志 rotation_frame=tool）。DROID 原始数据是世界系，DROID 权重用左乘（rotation_frame=world）。平移没有这个问题，全部是世界系下的 p_cur − p_prev。

在真机上确认：./task1-act.sh axis-test +x 应该沿底座 x 轴走，和夹爪朝向无关；axis-test +rz（右乘时）应该绕夹爪自身的轴转，夹爪朝下时看起来是"绕竖直轴反着转"。

5. 运动学

  • 正运动学（FK）：已知 7 个关节角，求末端位姿。就是把每节臂的长度和转向连乘起来（franka_description/robots/fr3/kinematics.yaml）。本项目的 eef_direct_kinematics.forward_kinematics() 和机器人 TF 对比，误差 0.02 mm。
  • 逆运动学（IK）：已知想要的末端位姿，求关节角。FR3 有 7 个关节，控制 6 个自由度，多出来一个冗余。
  • 雅可比矩阵 J：描述关节转得多快、末端就动得多快。反过来用，关节速度 = J⁻¹ × 末端速度，就叫"微分逆运动学"。J 不是方阵，所以用伪逆。
  • 奇异位形：某些姿势下（比如手臂完全伸直）J 会退化，硬算出来的关节速度会非常大。阻尼最小二乘（DLS）q̇ = Jᵀ(JJᵀ + λ²I)⁻¹v 在接近奇异时自动变保守。本项目跟踪器在最小奇异值 < 0.02 时直接拒绝执行，日志字段是 sigma_min；实测运行中最小值约 0.136，离奇异很远。

6. 机械臂怎么被控制

MoveIt 与 MoveIt Servo

MoveIt 是 ROS 的运动规划框架。MoveIt Servo 是其中的实时模块：持续告诉它"末端往哪个方向、以多快的速度动"，它就实时算出每个关节该转多快，并顺带做平滑、限速和碰撞检查。本项目 VR 采集时，franka_vr_vel.cpp 每个周期计算"目标 − 当前"的误差，乘以增益 2/s 得到末端速度（上限 0.30 m/s、0.975 rad/s），再交给 Servo 执行。

P 控制器与跟踪滞后

Direct 路径（绕过 Servo）

pi0.5 模型直接输出关节速度，由 pi05_direct_velocity_executor 下发，中间不经过 Servo。EEF 模型输出的是末端动作，所以 run_eef_direct.sh 用自己写的跟踪器（同样是增益 2/s 的规律，加上 DLS 微分逆运动学）把末端目标换算成关节速度，再交给 direct 执行器。task1-act.sh 默认走这条路，加 EEF_CONTROL=servo 可以退回 Servo。

安全保护（日志里常见的字样）

字样意思
translation_clipped单步限幅：每步平移 ≤ 6 mm、旋转 ≤ 0.035 rad，超出就按比例缩小
workspace_violation目标超出了 eef_workspace_bounds.yaml 定义的空间范围，锁停
tracking_violation目标领先实测超过 6 cm，说明机械臂没跟上
pose_jump实测位姿突然瞬移，说明 TF 数据源异常
限速 / 限加速度关节速度 ≤ 0.6 rad/s，加速度 ≤ 2 rad/s²（direct 执行器）
看门狗 watchdog超过 0.12 s 没收到新命令就停车
FAULT LATCHED一旦出现异常就锁定故障：停车并要求重启，不会自己恢复

8. 相机

  • 内参：焦距、光心和畸变系数，描述的是镜头本身。标定文件在 config/cameras/left_c922.yaml。
  • 外参：相机在世界坐标系里的位置和朝向，记录在 extrinsics.yaml。
  • 自动曝光：相机刚启动时画面很暗。训练数据每条示范开头几帧，腕部图像的平均亮度只有 16，正常约 100。
  • 缩放：相机输出 640×480，模型要 256×256。缩放方法（双线性还是双三次、是否裁剪、是否保持宽高比）必须和训练时一致。

9. 夹爪

  • Move：移动到指定宽度，用来张开夹爪。
  • Grasp：以一定的力闭合到目标宽度。最终宽度落在 [目标 − inner, 目标 + outer] 之内就算成功。本项目 inner 0.1、outer 0.2 m，几乎任何结果都会判定成功，所以"成功"不代表真的抓住了东西，要看实测宽度。
  • Homing：校准。夹爪上电后不做 homing，读数可能整体偏移；本项目实测，homing 结束时手指停在合拢位置。
  • 迟滞：模型输出 ≥ 0.6 才张开，≤ 0.4 才闭合，中间保持原状，避免在阈值附近反复开合。
  • 约定：本项目统一 0 = 闭合、1 = 张开。DROID 原始数据正好相反，训练时已经取反。

10. VLA 模型基础

VLA：Vision-Language-Action，输入图像和文字指令，输出机器人动作。本项目有两类：pi0.5（Physical Intelligence 的模型，用 openpi 微调），以及 Qwen3-VL-2B + ActionCodec（本组自研）。

状态与动作

状态："现在在哪"动作："接下来怎么动"
pi0.57 个关节角 + 夹爪关节速度
Task0 EEF 模型末端位置 (3) + 旋转向量 (3) + 夹爪开合 (1)平移增量 (3) + 旋转增量 (3) + 夹爪 (1)

注意，状态里的姿态是绝对的（"现在朝哪"），动作里的旋转是增量（"再转多少"）。两者都写成旋转向量，但含义完全不同。

Prompt 与指令

模型的输入是一段对话格式的文字：system 提示、用户消息、图像位置和状态占位 token，必须和训练时逐字一致。任务指令也必须和训练数据一致：Task0 训练用的是 place the red test tube in the red basket（tasks.json 里的 "0"）。之前部署时写成了 put the red test tube into the basket，模型从没见过这句话。DROID 权重见过大量不同的指令，可以随意写。

预训练、微调与泛化

  • 预训练：在大规模数据上学通用能力。DROID 数据集约有 7.6 万条轨迹、覆盖多种场景。
  • 微调：在自己的小数据上继续训练，适配具体任务。Task0 只有 29 条示范。
  • 一致性：微调数据的格式和含义要和预训练一致，才能继承预训练学到的能力。Task0 的旋转标签是工具系，DROID 是世界系，含义不一致，等于让模型重新学一遍旋转。
  • 分布外（OOD）：部署时遇到训练没见过的情况。数据越少，越容易"一出分布就不会"。Task0 的 29 条示范起点几乎完全相同（误差 < 0.3 mm），起点稍微偏一点模型就不适应，这就是加 home 模式的原因。
  • 数据增强：训练时随机改变亮度、对比度、裁剪方式和相机视角，让模型对这些变化不敏感。save_8000 没有开，save_4000（task1-act2.sh）开了。
为什么同样的数据，pi0.5 效果好？① pi0.5 的预训练更强，泛化能力更好；② 关节空间没有坐标系歧义，也没有旋转向量的 ±π 跳变；③ 动作标签直接用的是机械臂实际执行的关节速度，没有限幅，也没有"目标位姿领先实测"带来的偏差。

11. 数据采集与数据格式

  • 遥操作：人戴 VR 头显（Quest），手柄的位姿实时变成机械臂的目标位姿 fr3_vr_target，由 Servo 跟踪。
  • 录制器 lerobot_episode_recorder.py：以 30 Hz 记录图像、关节、末端位姿、夹爪和各种命令。
  • LeRobot 格式：每条示范一个目录，数值存在 parquet 表格里，图像存成 mp4 视频。
  • 训练缓存 droid_eef_15hz_v1.npz：训练脚本从 parquet 预先算好的 15 Hz 状态和动作块。

12. 排查方法

运行模式

模式动机械臂吗用途
dry-run不动用真实观测推理，检查模型输出是否合理
axis-test +z动一点不用模型，手工构造 5 步 × 3 mm 的动作，检查方向和控制链路
home动回到训练起点
默认（run）动完整任务

日志 policy.jsonl 里的事件

事件含义重点看什么
start启动参数与模型 metadatacheckpoint、指令、rotation_frame 对不对
pose_stable / armed启动检查通过起点位置是否接近训练起点
gripper_implausible / gripper_homed夹爪读数异常 / 已完成校准homing 后张开读数应约为 0.08
observation一次观测eef_state、gripper_width；对应图像在 observations/
chunk一个动作块policy_latency（推理耗时）
action每一步目标位姿、实测位姿、target_lead_m、是否限幅
trackdirect 跟踪器的采样记录关节速度、sigma_min
settled到位等待结束timed_out：是否超时
gripper_request / gripper_done夹爪命令 / 执行结果闭合后宽度：≈0.013 是夹住了，≈0 是空抓
observation_waiting等不到观测blocker 字段写着缺的是什么
fault锁停reason 字段
complete正常结束reason 字段

失败归类

  1. 一启动就被拒绝：看终端最后一行的 REFUSED 或 RuntimeError，常见原因有服务和权重不匹配、夹爪没张开、指令不一致。
  2. 运行中出现 FAULT LATCHED：控制层或安全层的问题，看 fault 事件里写的原因。
  3. 跑完没报错，但任务失败：是模型的问题。对比 observations/ 里的图像和训练数据，看模型往哪走、在哪闭合了夹爪。
