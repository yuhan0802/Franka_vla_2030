使用：服务 + 适配器 + 握手
dry-run / run 时才发生
① 启动模型服务（GPU 机 mac_63）
ssh mac_63 → scp server/deploy_*.py → 远端 tmux。8098 已在监听就直接复用，不重启
CUDA_VISIBLE_DEVICES=1 python deploy_…_eef.py \
  --checkpoint …/save_10000_chkpt \
  --actioncodec … --state-stats … --port 8098
② 启动适配器（机器人主机容器）
eef_pose_direct_adapter.py \
  --expected-checkpoint …/save_10000_chkpt \
  --expected-actioncodec … --expected-state-stats … \
  --expected-model-image-size 256 \
  --expected-action-normalization franka_mulaw \
  --expected-action-mulaw-mu 9.0 \
  --action-gain 1.0 0.8 1.0 1.0 1.0 1.0 \
  --execute-horizon 10 --home-position …
③ 握手核对：服务端 metadata ⇄ 期望值
✅ 全部一致
开始推理 → 动作块 → 机械臂
⛔ 任一不符
拒绝运行："stop the stale server first"
（端口上跑的是旧权重）
✔ 允许的临时覆盖（只对本次生效，不改 JSON）
EEF_CONTROL=servoEEF_EXECUTE_HORIZON=5EEF_MAX_CHUNKS=3EEF_MAX_ACTIONS=60EEF_RUN_DIR=…EEF_TASK_CONFIG=/path/other.json
用于做实验（如「预测 15 执行 5」），确认有效后再写回 JSON。
✘ 无效覆盖（会被 JSON 解析结果覆盖）
EEF_CHECKPOINT=…EEF_SERVER_HOST=…EEF_SERVER_PORT=…EEF_INSTRUCTION=…
模型身份只认 JSON。要换权重：新增一个 model key 并加进任务的 models[]。
pi0.5 关节注册表 vla_instruction_weights.json（另一种协议，不能混用）
一个 id 绑一个 checkpoint；direct.runtime_from 沿链继承运行参数，只取链尾条目的 runtime：
task0-fsp-demo10runtime_from →task1runtime_from →task2.runtime= 2000 步 · 0.6 rad/s · 2.0 rad/s²
因此 task1、demo10 条目里自己写的 runtime（240 步 / 0.15 rad/s）在 run_task.sh 中不生效。用 ./run_task.sh <id> show 查看实际值。
